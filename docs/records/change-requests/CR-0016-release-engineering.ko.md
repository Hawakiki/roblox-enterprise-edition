# 릴리스의 번호, 관문, 게시

> 본 문서는 CR-0016 영문 정본의 번역본이다. 내용이 상충하는 경우 영문 정본이 우선한다.

## 1. 요약

이제 회사의 릴리스는 표준과 워크플로를 따른다.
뒤늦게 작성하는 EE-STD-0008 이 릴리스의 번호, 준비, 태그, 게시, 시기를 정한다.
태그를 push 하면 워크플로가 돈다. 달력을 확인하고, 모든 검사를 돌리고, 플레이스를 빌드하고, 릴리스되는 변경 요청에서 릴리스 노트를 만든다. 그리고 기록상 결재권자가 승인하면 GitHub 에 릴리스를 게시한다.

## 2. 배경

EE-STD-0008 의 예약 문서는 첫 릴리스와 함께 표준을 작성한다고 하였다.
1.0.0 은 그 표준 없이 릴리스되었다(CR-0014). 알고 보니 1.0.0 은 태평양 일부 지역이 아직 금요일이던 때에 릴리스되기도 하였다.

회사에는 지속적 배포가 없다. 릴리스는 태그일 뿐 그 이상이 아니며, 릴리스 노트는 한 번도 쓰인 적이 없다.

전결 규정인 EE-POL-0003 은 조직도와 함께 작성하도록 예약되어 있으며, 기록상 결재권자는 조직도를 보류하였다.
따라서 EE-POL-0003 은 예약된 채로 둔다. 배포의 승인은 누가 승인하는지를 이미 정한 문서인 EE-POL-0004 §7 과 EE-POL-0006 §4 에 근거한다.

기록상 결재권자는 변경 동결 두 가지를 결정하였다.

- 지구 어딘가가 금요일인 동안은 배포하지 아니한다.
- 지구 어딘가가 2038년 1월 19일인 동안은 배포하지 아니한다. 부호 있는 32비트 초 단위 시각이 넘치는 날이다.

## 3. 범위

- 확보해 둔 번호에 작성하는 엔터프라이즈 버전 표준 EE-STD-0008
- 동결 중의 배포를 거부하는 `scripts/lib/ReleaseCalendar.luau` 와 `scripts/release_gate.luau`, 그리고 2038년과 2106년까지 닿는 테스트
- 릴리스의 커밋이 인용하는 변경 요청에서 릴리스 노트를 만드는 `scripts/lib/ReleaseNotes.luau` 와 `scripts/release_notes.luau`, 그리고 테스트
- `v*` 태그로 실행되는 `.github/workflows/release.yml`. 세 작업으로 이루어진다.
  - 달력
  - 모든 검사, 플레이스, 릴리스 노트
  - `production` 환경에서의 게시
- `production` 환경을 파일로 둔 `.github/environments/production.json`. 기록상 결재권자의 검토를 요구하며 `v*` 태그만 받는다. 본 요청의 머지가 승인되면 `gh api` 로 적용한다.
- 머지가 승인되면, 동결이 아닌 때에 1.0.0 의 릴리스 노트를 만들어 GitHub 릴리스로 게시한다.
- `README.md`, `README.ko.md`, `AGENTS.md`: 릴리스하는 방법과 읽을 곳

## 4. 영향도 평가

| 영역 | 영향 |
|---|---|
| 릴리스 | 태그는 모든 검사를 통과하고 기록상 결재권자가 승인한 뒤에만 게시된다. |
| 달력 | 매주 약 50시간, 그리고 2038년 1월 19일 앞뒤의 50시간 동안은 배포할 수 없다. |
| 릴리스 노트 | 아무도 쓰지 않으며, 회사가 이미 보관하는 기록에서 만들어진다. |
| 문서 분량 | 확보해 둔 표준 하나를 작성한다. 추가하는 것은 없다. |

## 5. 원복 계획

본 변경의 머지 커밋을 되돌리고, `gh api` 로 `production` 환경을 지우며, 본 변경이 게시한 GitHub 릴리스를 지운다.
태그는 ruleset 이 요구하는 대로 남는다.
