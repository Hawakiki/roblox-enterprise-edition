# EnterpriseEdition 1.1.0 릴리스

> 본 문서는 CR-0017 영문 정본의 번역본이다. 내용이 상충하는 경우 영문 정본이 우선한다.

## 1. 요약

본 변경 요청은 EnterpriseEdition 1.1.0 을 릴리스한다. EE-STD-0008 에 따라 만드는 첫 릴리스이자, 릴리스 워크플로가 배포하는 첫 릴리스이다.
모든 검사가 실행될 수 없을 때 실패하게 하는 CR-0015 와, 릴리스의 번호·관문·게시를 정하고 배포 달력을 두는 CR-0016 을 담는다.
준비 과정에서, 1.0.0 에 이미 릴리스된 CR-0014 가 릴리스 노트에 한 번 더 실릴 뻔했음이 드러났다. 이제 변경 요청은 그것을 인용하는 첫 릴리스에 속한다.
한 번도 쓰인 적 없는 1.0.0 의 릴리스 노트도 함께 만들어 게시한다.

## 2. 배경

1.0.0 이후 CR-0015 와 CR-0016 이 승인되어 `develop` 에 들어왔다.
둘은 표준 하나, 워크플로, 달력, 실행할 수 없으면 실패하는 검사를 추가한다. 1.0.0 이 내보낸 계약, 서비스 토큰, 리모트, 저장 스키마, 승인된 문서의 의무는 하나도 바꾸지 않는다.
따라서 본 릴리스의 번호는 1.1.0 이다(EE-STD-0008 §4.3).

본 요청을 등록하기 전에 `v1.0.0` 이후 인용된 변경 요청을 나열하였다.
`release/1.0.0` 을 `develop` 으로 되돌려 머지한 커밋(`df3a4ea`)이 CR-0014 를 인용하며, 이 커밋은 `v1.0.0` 뒤에 있다.
승인된 EE-STD-0008 §5.3 은 이전 릴리스 태그 이후의 커밋이 인용하는 모든 변경 요청을 싣게 하므로, CR-0014 를 두 번 릴리스할 뻔하였다.

CR-0016 은 1.0.0 릴리스 노트의 게시를 뒤따르는 릴리스 요청에 맡겼다.

## 3. 범위

- `develop` 에서 딴 `release/1.1.0`(EE-POL-0004 §5)
- `scripts/lib/ReleaseNotes.luau` 와 `scripts/release_notes.luau`: 이전 릴리스의 이력이 인용하는 변경 요청은 릴리스 노트에서 뺀다. 테스트를 포함한다.
- 이를 반영하여 개정하는 EE-STD-0008 §5.3. 1.1.0 으로 `In Review`
- `AGENTS.md`: 지뢰
- push 하지 않는 새 clone 에서의 리허설: 그 안에서 릴리스를 머지하고 태그를 달아, 모든 검사를 돌리고, 1.1.0 의 릴리스 노트를 만들고, 플레이스를 빌드한다.
- 승인 후, 변경 동결이 아닌 때에:
  - 1.0.0 의 릴리스 노트를 만들고, 그 태그에서 1.0.0 의 플레이스를 빌드하여, 둘을 `v1.0.0` 의 GitHub 릴리스로 게시한다. 1.1.0 이 최신 릴리스가 되도록 이를 먼저 한다.
  - `release/1.1.0` 을 `main` 에 `--no-ff` 로 머지하고, 그 머지 커밋에 `v1.1.0` 태그를 달고, `release/1.1.0` 을 `develop` 으로 되돌려 머지한다.
- `main`, `develop`, 태그의 push 와 `production` 환경에서의 배포 승인은 기록상 결재권자에게 맡긴다.
  워크플로가 1.1.0 을 어떻게 배포하였는지는 뒤따르는 요청이 기록한다.

## 4. 영향도 평가

| 영역 | 영향 |
|---|---|
| `main` | 머지 커밋 하나로 1.0.0 에서 1.1.0 으로 옮겨 간다. |
| 릴리스 | 1.0.0 이 GitHub 에서 릴리스 노트와 플레이스를 얻는다. 1.1.0 은 워크플로가 배포하는 첫 릴리스이다. |
| Dependabot | `main` 에서 설정을 읽고 동작을 시작한다. |
| 문서 분량 | 표준 하나의 한 문장을 개정한다. 추가하는 것은 없다. |

## 5. 원복 계획

`v1.1.0` 과 `v1.0.0` 의 GitHub 릴리스를 지우고, `main` 과 `develop` 의 머지 커밋을 되돌린다.
태그는 ruleset 이 요구하는 대로 남는다. 정정은 1.1.1 로 릴리스한다(EE-STD-0008 §4.6).
