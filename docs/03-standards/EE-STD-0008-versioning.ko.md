# 엔터프라이즈 버전 표기 표준

> 본 문서는 EE-STD-0008 영문 정본의 번역본이다. 내용이 상충하는 경우 영문 정본이 우선한다.

## 1. 목적

본 표준은 EnterpriseEdition 릴리스의 번호, 준비, 태그, 배포 방식과, 배포할 수 없는 때를 정한다.

## 2. 적용 범위

1. 본 표준은 핫픽스를 포함한 모든 릴리스와 그 배포에 적용된다.
2. 1.0.0 릴리스는 본 표준보다 먼저 나왔다(CR-0014).
   릴리스 노트 없이, 그리고 태평양 일부 지역이 아직 금요일이던 때에 릴리스되었다.
   태그는 움직이지 않으므로(§4) 1.0.0 은 릴리스된 그대로 둔다.
   그 릴리스 노트는 §5 에 따라 만들어, 변경 동결이 아닌 때에 한 번 게시한다(CR-0016).

## 3. 정의

| 용어 | 뜻 |
|---|---|
| 릴리스 | `main` 의 태그가 이름 붙인 EnterpriseEdition 의 한 버전 |
| 배포 | 릴리스의 게시. 현재는 플레이스를 첨부한 GitHub 릴리스 |
| 플레이스 | `rojo build` 가 `default.project.json` 으로 만드는 파일 |
| 변경 동결 | 어떤 릴리스도 배포하지 않는 기간 |
| 지구 어딘가 | 한 날짜가 존재할 수 있는 모든 곳. 그 날짜에 가장 먼저 들어가는 UTC+14 부터 가장 늦게 나오는 UTC-12 까지이며, 모든 날짜는 50시간 동안 존재한다. |

## 4. 버전 번호

1. 릴리스의 번호는 Semantic Versioning 2.0.0 이 정한 대로 `MAJOR.MINOR.PATCH` 이다.
2. 템플릿 사용자가 기대는 것, 곧 계약, 서비스 토큰, 리모트, 저장 레코드의 스키마, 승인된 문서의 의무를 제거하거나 바꾸는 릴리스는 MAJOR 를 올린다.
3. 무엇인가를 추가하고 아무것도 바꾸지 않는 릴리스는 MINOR 를 올린다.
4. 정정만 하는 릴리스는 PATCH 를 올린다.
5. 릴리스의 태그는 `v1.1.0` 처럼 `v` 뒤에 번호를 붙인 것이며, 릴리스를 `main` 에 들이는 머지 커밋에 단다.
6. 태그는 움직이지 않고 지워지지 않는다.
   잘못된 것으로 드러난 릴리스 뒤에는 새 릴리스가 온다.
7. 프리릴리스 식별자는 쓰지 않는다. 회사는 책임지지 못할 것을 릴리스하지 아니한다.

## 5. 릴리스 준비

1. 릴리스는 `develop` 에서 딴 `release/<version>` 에서, 그 릴리스만의 변경 요청에 따라 준비한다(EE-POL-0004 §5, §6).
2. 릴리스 브랜치는 `main` 과 `develop` 에 각각 `--no-ff` 로, 기록상 결재권자의 승인을 받아 머지한다(EE-POL-0004 §7).
3. 릴리스 노트는 `lune run scripts/release_notes <tag>` 로 만들며, 손으로 쓰지 않는다.
   이전 릴리스 태그 이후의 커밋이 인용하는 모든 변경 요청을 두 언어의 제목과 영문판의 요약과 함께 싣는다.
4. 따라서 변경 요청의 요약은 대중이 읽을 것처럼 쓴다. 실제로 대중이 읽기 때문이다.

## 6. 배포

1. 릴리스는 그 태그를 push 하여 배포하며, 이로써 `.github/workflows/release.yml` 이 실행된다.
2. 워크플로는 달력을 확인하고(§7), `tools/check` 를 돌리고, 플레이스를 한 번 빌드하고, 릴리스 노트를 만든다.
3. 그다음 게시는 `production` 환경에서 기록상 결재권자가 배포를 승인하기를 기다린다(EE-POL-0004 §7, EE-POL-0006 §4).
   이 환경은 `v*` 태그만 받으며, `.github/environments/` 에 파일로 보관한다.
4. 승인은 동결이 시작된 뒤에 올 수 있으므로, 워크플로는 게시하기 전에 달력을 한 번 더 확인한다.
5. 게시되는 것은 빌드된 그대로의 플레이스와 릴리스 노트이며, 태그의 GitHub 릴리스로 게시된다.
6. 달력이 거부한 배포는 미뤄지지 않는다.
   동결이 지난 뒤, `scripts/release_gate` 가 알려 주는 때에 워크플로를 다시 실행한다.

## 7. 변경 동결

1. 지구 어딘가가 금요일인 동안, 즉 매주 UTC 목요일 10:00 부터 토요일 12:00 까지는 어떤 릴리스도 배포하지 아니한다.
2. 지구 어딘가가 2038년 1월 19일인 동안, 즉 UTC 2038년 1월 18일 10:00 부터 1월 20일 12:00 까지는 어떤 릴리스도 배포하지 아니한다.
   그날 UTC 03:14:07 에 1970년 이후의 초를 세는 부호 있는 32비트 값이 넘친다.
3. 두 번째 동결은 진단이 아니라 예방 조치이다.
   EnterpriseEdition 은 시각을 Luau number 에 담으며, 이는 64비트 부동소수점이라 2038년에도, 부호 없는 32비트 값이 넘치는 2106년에도 넘치지 않는다.
   달력의 테스트는 두 해를 모두 넘어선다.
4. 핫픽스도 예외가 아니다. 긴급 변경은 더 빨리 제출하는 변경 요청이지(EE-POL-0004 §9), 금요일에 배포하는 변경 요청이 아니다.
5. 달력은 `scripts/lib/ReleaseCalendar.luau` 이며, `scripts/release_gate.luau` 가 이를 적용한다.

## 8. 시행

1. 릴리스 워크플로가 §6 과 §7 을 강제한다.
   마지막 작업은 기록상 결재권자가 승인하기 전에는 실행될 수 없고, 변경 동결 중에는 `scripts/release_gate` 가 이를 실패시킨다.
2. ruleset `release-tags-never-move` 가 §4.6 을 강제한다.
3. 본 표준은 자체 checkpatch 규칙을 두지 아니한다.
