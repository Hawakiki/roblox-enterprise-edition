# Enterprise Versioning Standard

## 1. Purpose

This standard sets how a release of EnterpriseEdition is numbered, prepared, tagged and deployed, and when it may not be deployed at all.

## 2. Scope

1. This standard applies to every release and to every deployment of one, hotfixes included.
2. Release 1.0.0 predates it (CR-0014).
   It was released without notes, and while it was still Friday in parts of the Pacific.
   It stands as released, for a tag never moves (§4).
   Its notes are generated under §5 and published once, outside a change freeze (CR-0016).

## 3. Definitions

| Term | Meaning |
|---|---|
| Release | A version of EnterpriseEdition, named by a tag on `main`. |
| Deployment | The publication of a release: at present, a GitHub release with the place attached. |
| Place | The file that `rojo build` makes from `default.project.json`. |
| Change freeze | A period during which no release is deployed. |
| Anywhere on Earth | Wherever a date can be, from UTC+14, which enters it first, to UTC-12, which leaves it last: 50 hours for every date. |

## 4. Version Numbers

1. A release is numbered `MAJOR.MINOR.PATCH`, as Semantic Versioning 2.0.0 sets out.
2. MAJOR is incremented when a release removes or alters something that a user of the template relies on: a contract, a service token, a remote, the schema of a stored record, or an obligation of an approved document.
3. MINOR is incremented when a release adds something and alters nothing.
4. PATCH is incremented when a release only corrects.
5. The tag of a release is `v` followed by its number, as in `v1.1.0`, and is set on the merge commit that brings the release into `main`.
6. A tag never moves and is never deleted.
   A release that turns out wrong is followed by a new one.
7. Pre-release identifiers are not used. The Company releases nothing it does not stand behind.

## 5. Preparing a Release

1. A release is prepared on `release/<version>`, taken from `develop`, under a change request of its own (EE-POL-0004 §5 and §6).
2. The release branch is merged into `main` and into `develop`, each time with `--no-ff` and the approval of the Approver of record (EE-POL-0004 §7).
3. The notes of a release are generated by `lune run scripts/release_notes <tag>`, never written.
   They list every change request cited by a commit since the previous release tag, with its title in both languages and the summary of its English version.
4. A change request is therefore summarized as though its summary will be read by the public, because it will be.

## 6. Deployment

1. A release is deployed by pushing its tag, which runs `.github/workflows/release.yml`.
2. The workflow consults the calendar (§7), runs `tools/check`, builds the place once and generates the notes.
3. The publication then waits in the environment `production` for the Approver of record to approve the deployment (EE-POL-0004 §7, EE-POL-0006 §4).
   The environment admits tags `v*` only, and is kept as files in `.github/environments/`.
4. Before it publishes, the workflow consults the calendar again, for an approval may arrive after a freeze has begun.
5. What is published is what was built: the place and the notes, as the GitHub release of the tag.
6. A deployment refused by the calendar is not postponed.
   The workflow is run again once the freeze has passed, at the moment that `scripts/release_gate` names.

## 7. Change Freezes

1. No release is deployed while it is Friday anywhere on Earth: from Thursday 10:00 to Saturday 12:00 UTC, every week.
2. No release is deployed while it is 19 January 2038 anywhere on Earth: from 18 January 2038 10:00 to 20 January 2038 12:00 UTC.
   At 03:14:07 UTC that day, a signed 32-bit count of seconds since 1970 overflows.
3. The second freeze is a precaution, not a diagnosis.
   EnterpriseEdition keeps time in Luau numbers, which are 64-bit floating point and overflow neither in 2038 nor in 2106, when an unsigned 32-bit count does.
   The tests of the calendar reach past both.
4. A hotfix is no exception. An emergency is a change request filed faster (EE-POL-0004 §9), not one deployed on a Friday.
5. The calendar is `scripts/lib/ReleaseCalendar.luau`, and `scripts/release_gate.luau` applies it.

## 8. Enforcement

1. The release workflow enforces §6 and §7.
   Its last job cannot run before the Approver of record approves it, and `scripts/release_gate` fails it during a change freeze.
2. The ruleset `release-tags-never-move` enforces §4.6.
3. This standard mandates no checkpatch rule of its own.
