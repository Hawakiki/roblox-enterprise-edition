# 생성자는 any 캐스트로 자기 계약을 반환한다

> 본 문서는 ADR-0001 영문 정본의 번역본이다. 내용이 상충하는 경우 영문 정본이 우선한다.

## 1. 배경

이 결정은 애플리케이션 프레임워크와 함께 CR-0007 에서 내려졌다. 회사가 창립 때부터 아키텍처 결정 양식을 갖추고도 한 건도 등록하지 않았음을 알아차린 하루 뒤에야 기록된다.

회사는 서비스를 클래스로 작성한다. 각 클래스는 메타테이블이며, 그 메서드는 클래스 자신을 `self` 로 받는다.
각 클래스는 계약 뒤에서 일한다. 계약은 `I<Name>` 모듈에 있는 테이블 타입이고, 그 메서드는 `self: any` 를 받는다. 어떤 클래스가 자기를 구현할지 계약은 모르기 때문이다(EE-STD-0006 §6).
서비스를 쓰는 코드는 그 계약만 알아야 하며, 그래야 가짜가 그 자리를 대신할 수 있다.

클래스 인스턴스는 계약이 들어갈 자리에 쉽게 들어가지 않는다.
luau-lsp 1.69.0 에서 옛 타입 솔버는 인스턴스를 계약으로 반환하는 것을 거부하고, 새 솔버는 받아들인다.
회사는 두 솔버로 모두 코드를 검사한다(EE-STD-0001 §4).

## 2. 결정

우리는 모든 생성자가 자기가 구현하는 계약을 반환하게 하며, 이를 위해 인스턴스를 `any` 로 캐스트한다. 예: `return setmetatable(state, Class) :: any`.
캐스트는 그 한 지점에서 검사기를 끈다. 그래서 모든 클래스는 자기가 구현하는 메서드를, 타입이 그 계약인 `_implements` 테이블에 따로 선언하고, 검사기는 대신 그 테이블을 계약에 맞춰 검사한다.
우리는 두 타입 솔버로 모두 검사한다. `_implements` 의 메서드를 계약의 시그니처에 맞춰 검사하는 것은 옛 솔버뿐이기 때문이다.

## 3. 결과

| 구분 | 결과 |
|---|---|
| 긍정 | 코드는 계약에만 의존한다. 가짜는 평범한 테이블로 계약을 구현한다. |
| 긍정 | 옛 솔버에서는 매개변수, 인자, 반환이 계약과 어긋난 메서드가 `_implements` 가 그것을 선언한 곳에서 보고된다. |
| 부정 | 캐스트가 생성자를 검사기에서 가린다. 생성자가 무엇을 반환하든 계약으로 통과한다. |
| 부정 | 새 솔버는 `_implements` 에 대해 각 메서드가 있는지만 검사하고 그 이상은 보지 않는다. `self: any` 를 받는 계약 메서드에 대해서는 매개변수, 인자, 반환의 차이를 보고하지 않는다. 2026-10-31 에 세 가지로 어긋나게 한 메서드 세 개는 옛 솔버에서 오류 세 건을, 새 솔버에서 0 건을 냈다. |
| 부정 | 클래스마다 다섯 단계를 거친다. 계약, 클래스, `_implements`, 캐스트, 서비스 토큰이다. |
| 중립 | 본 기록 시점에 `src/` 에는 14개 파일에 `any` 캐스트 17개, `_implements` 테이블 15개가 있다. |

## 4. 검토한 대안

| 대안 | 채택하지 않은 이유 |
|---|---|
| 생성자가 클래스를 반환하고 호출하는 쪽이 클래스에 의존한다 | 호출하는 쪽이 구현에 의존하게 되고, 가짜가 클래스의 모든 메서드 없이는 그 자리를 대신할 수 없다. |
| 생성자가 캐스트 없이 인스턴스를 계약으로 반환한다 | 옛 솔버가 거부한다. |
| 새 솔버로만 검사한다 | 계약과 어긋난 메서드가 보고되지 않는다. |
| `type function` 으로 구현을 선언한다(2026-10-31 검토) | 옛 솔버가 그 문법을 받아들이지 않는다. luau-lsp 1.69.0 에서 공용 모듈이 내보낸 `type function` 은 아무것도 검사하지 않으며, 클래스 파일마다 복사하면 옛 솔버로 일하는 사람에게는 그 파일이 모두 빨갛게 보인다. |
